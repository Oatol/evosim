## 新一轮需求评估前的性能实测（未改一行代码）

用户这一轮提了 8 件事，其中两件是重量级方向问题（每像素环境属性、要不要换架构），
明确要求"先讨论可行性，不要改动"。所以在讨论前先把**性能账**量清楚——否则"要不要换 GPU/换架构"
只能靠猜。

### 实测数据（Windows / Chrome / 200×150 = 30000 格）

| 项 | 实测 | 说明 |
|---|---|---|
| `world.step()` 稀疏（9 只） | 0.027 ms/tick | |
| `world.step()` 满载（1517 只） | **2.0 ms/tick** | ≈1.3 µs/只 |
| `renderer.render()` zoom 2 / 4 | 0.002 / 0.003 ms/帧 | 低倍率几乎免费 |
| `renderer.render()` zoom 8 / 16 | 0.54 / 0.13 ms/帧 | 高倍率 drawImage 放大 |
| `render()` 含全量层重建 | 0.26–0.30 ms/帧 | 30k 像素重涂 0.043 ms |
| 1× | 144 fps · 60 tps | 完全流畅 |
| 10× | **4 fps** · 600 tps | 模拟吃满线程 |
| 50× | **4.6 fps** · 1838 tps | 追不上 3000 tps 目标 |
| 单只大脑前向 | 1.01 µs | 扁平化批处理 0.68 µs（仅 1.47×） |
| 全分辨率 5 点扩散 | 0.13 ms/次 | 60Hz 只要 8 ms/s |

### 三条结论

1. **渲染不是瓶颈**：0.1–0.5 ms/帧。换 WebGL/WebGPU 只省不到 1% 的帧时间 → 不值得。
2. **瓶颈是 CPU 模拟**：每只生物 ~1.3 µs/tick，其中**大脑前向就占 1.0 µs**（40→12→5）。
   10× 时 600 tick/s × 2 ms = 1.2 s/s，线程被模拟吃光，帧率塌到 4 fps。
3. **每像素场其实很便宜**：全分辨率扩散 0.13 ms/次。只要**场更新频率与 tick 解耦**（按 60Hz 墙钟走，
   不随倍速），5 个场加起来也只有 4% 的 CPU。之前"必须用粗粒度场"的判断，是在"每 tick 都扩散"的
   前提下算的——那个前提现在可以不要。

### 三个必须守住的不变量（踩过才知道）

1. **`CELL_DEFS` 数组下标必须等于 id**。我一开始把地形（9–12）写在储食/再生/刺（13–15）前面，
   `def(id)` 按下标取就拿到别人的定义 → STORAGE 标志位丢失 → 繁殖阈值失效 → 第 194 tick 分叉。
   现在有 `order_tests` 守着。
2. **压缩死亡个体必须稳定**（`Vec::retain`），不能 swap-remove。阶段 B 的结算顺序是"对个体数组洗一次牌"，
   数组顺序一变，洗牌出来的访问序列就变。
3. **构造 `Organism` 必须照抄那 545 次高斯调用**（虽然立刻被 `copyFrom` 覆盖掉）——
   JS 的 `new Brain()` 会先随机初始化，浪费的随机数也占序列。

### 浮点这件事的实测结论

`Math.log`（V8 的 fdlibm 移植）与 Rust `f64::ln` 在个别输入上差 1–2 ulp：
200 个高斯样本里 **6 个不同**。但大脑权重/激活值最终存 f32，差异被舍入吸收，
所以状态摘要仍然全等（5 种子 × 2000 tick 验证）。若将来真出现分歧，
只需把 `jsmath.rs` 换成 fdlibm 移植版，调用点不用改。

### 踩到的坑：egui-wgpu 的 `RenderPass<'static>`

`egui_wgpu::Renderer::render(&self, render_pass: &mut wgpu::RenderPass<'static>, ...)`

## Rust M3（第二批）：检视器 / 物种面板 / 曲线 + 平铺 bug 修复（2026-10-17）

### 先修的那个 bug：缩小后世界被重复平铺

着色器原来**无条件**对世界坐标取模 → 世界比视口小时，屏幕被同一个世界铺满。
1.x 也踩过同一个坑。修法：**逐方向判断**

```wgsl
if (world_px.x < u.viewport.x) {   // 世界比视口窄
    if (col < 0 || col >= cols) { return BACKDROP; }   // 越界 → 背景色
} else {
    col = ((col % cols) + cols) % cols;                // 才环绕
}
```

背景色刻意比"空格"（#0b1020）更暗（#05070c），这样世界边界一眼可见；
清屏色也统一成它。回归测试 `no_tiling_when_world_smaller_than_viewport`：
8×8 世界 @zoom=2 塞进 80×80 视口，断言世界内部渲染出墙、四角是背景色。

## 高亮层序修复 + M5（字体子集 / 单 exe / LTO）（2026-10-17 傍晚）

### 高亮仍然浮在窗口之上（第二次修）

第一次修错了，原因是**两层误解**：

1. `Context::layer_painter(id)` **只是构造一个 Painter，不会创建图层**——图层要等到
   真正 `add` 图形时才登记。所以上一版"帧首先登记一次"完全是空操作。
2. 更关键的是 `GraphicLayers::drain()` 的绘制顺序：同一 Order 内**先画登记在
   `area_order` 里的 Area（窗口）**，再画"没登记成 Area"的图层。我们的高亮不是 Area，
   所以**永远排在所有窗口之后**——不管什么时候创建。

修法：换成 `Order::Background`（egui 注释原文 "Painted behind all floating windows"），
并把图层提取成 `ui::highlight_layer()` 便于测试。

**回归测试** `highlight_is_painted_below_windows`：往 Middle 层画窗口底色、再往高亮层画描边，
断言描边排在底色之前。**做了变异验证**（把图层改回 Middle → 测试立刻红）。

踩的坑：
- `draw()` 里会 `st.highlights.clear()`，测试不能手工塞高亮，必须走"选中个体"的真实路径
- `add_organism()` 会**重写** `org.id`，必须用它的返回值（否则 selected_org 指向不存在的 id）
- headless 下 `egui::Window` 第一帧是淡入（opacity 0 → 形状被剔成 `Shape::Noop`），
  所以最终改成不依赖窗口渲染的层序测试

### M5：字体子集 + 单 exe + release 调优

- `tools/subset-font.py`：扫全部 `.rs`/`.wgsl` 收集非 ASCII 字符（1000 个），

  576 KB → 201 KB，12px 屏幕上 hinting 用不上）
- `ui.rs`：`include_bytes!` 内嵌子集，**系统字体挂在它后面当后备**——
